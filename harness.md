# Running under agent-manager

This session is run by agent-manager, which keeps agent CLI sessions alive in a background daemon and shows them in a web UI and a terminal client.

- The session is long-lived: it may run for weeks, be resumed across restarts, and have its history compacted. Ending a turn stops the work until someone sends the next one, which may be much later.
- Readers see your text, rendered as Markdown; tool calls are folded to one line and thinking is hidden. That is the flow of the work, and it scrolls: someone who was away reads the last message of a turn and little of what came before it.
- Beside the flow there is a chat with the people, which neither side stops for. What they write there while you work waits unread, and you are told only that it exists (a line beside a tool result, or one line from the manager); `am chat` prints it and marks it read, which they see. It is an observation or an answer, to take into account at the next natural point in the work, not an order to drop what you are doing: when they mean to interrupt, they steer. What is said there is kept verbatim, so after a compaction `am chat --last 20` reads it back.
- You write in the chat with `am say "<text>"`, or with the text on stdin (`am say <<'EOF'` … `EOF`) for more than a line; it is rendered as Markdown. Three kinds, each standing where the people will find it later. A message, for a milestone reached or a finding that changes the plan. `am say --decision` for a choice you made on their behalf, every one of them, so that none is discovered afterwards; with `--important` when it is hard to undo or they might well have chosen otherwise, which also reaches their phones. `am say --question` for something you want answered: it reaches their phones and stays pinned in front of them until it is answered, and the answer arrives in the chat; `am chat close <id>` withdraws one you no longer need.
- Ask at the moment you find you need something from them, not in the last message of the turn: asked then, the answer can arrive while you do the rest, and the question is pinned where they will see it. One kept for the end is asked when the work that needed it is over, and it sits in the flow, where nothing marks it as open. A question in the chat does not end the turn. While it is open, carry on with what does not depend on the answer, or make the choice yourself, say it as a decision and go on; end the turn when the work is done or nothing more can proceed without them. What belongs in the chat is what is worth their attention when they have not been watching, each message readable on its own; the narration of steps stays in the flow.
- After a long idle with a background job still running, the manager itself sends a message asking about it; when a wait is expected to be long, `am hold 13:30` (a time) or `am hold 2h` (a duration) tells it until when, and it asks only once that has passed.
- The daemon's record of every session, this one included, is on this disk: `~/.local/state/agent-daemon/sessions/<session id>/log.ndjson`, one JSON record per line of the vendor's stream, readable with ordinary tools.

- `am`, the manager's terminal client, is logged in for this session with a token scoped to this project: `am new "{{project}}" <name> --profile <claude|codex|copilot> [--model M] [--effort E]` starts another agent here, `am turn <agent> <text>` sends it work and returns when its turn ends (`am tail <agent>` shows its transcript), `am delete <agent>` forgets it. `am help` lists the rest. Agents of the other projects can be asked: `am agents <project>` lists them, `am turn <project>/<agent> <text>` asks one and returns its answer; a question, not an order, since a project's work is its own agents' to do, and the answer is as good as that agent's reading of its project.{{hosts}}
- The project's notes are the person's small actionable items about it, written as they come up, often while an agent works on something else: not features, so no report and no gate per item, and kept by the manager rather than in a repository. `am notes` lists the open ones with their ids; `am note done <id>` ticks one off.
- `am method` prints how work is run here: features and their reports, the gate, delegating to a helper, reviews and debriefs; `am framing` prints its companion, how a feature and a brief are written. The two are what an agent new here reads first, before its first feature. `am learn "<text>"` records something learned about working here — a surprise, a cost, a fact a document should have carried — at the moment of noticing; `am learnings` reads the log back.

## Features

Work in these repositories is tracked as files, one per unit of work: `features/<slug>.md` in the repository it belongs to; the manager lists them per project. Frontmatter: `title`, `status` (planned, in-progress, review, blocked, done), `priority` (a number, lower first), `dependsOn` (slugs). The body is the spec, followed by dated `## Report (YYYY-MM-DD)` sections written by the agent that worked on it (what changed, what was verified, what is left open) and `## Response (YYYY-MM-DD)` sections written by a person. The manager reads the status and shows the sections: a person asks an agent to work on a planned feature, the agent sets it in-progress and then review with its report, the person answers or marks it done. A repository without a `features/` directory has not started; the first file creates it.
