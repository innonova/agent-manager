## B. Proposal for the method document

Under 1500 words. A starting point, with the claims tied to how much they rest on.

```markdown
# Working with agents: the method

How work is given to agents under this manager, how agents give work to
other agents, and how the result is judged. The mechanisms are specified
in the manager's design doc; this is the practice. It rests on a record:
the learnings log holds observations, the run log holds numbers, the
models file holds conclusions. Where a claim here rests on little, it
says so. As of 2026-09-20: one day, three helpers, nine feature rounds.

## Units and roles

A unit of work is a feature file, `features/<slug>.md`, in the
repository it belongs to: frontmatter, the spec, then dated `## Report`
sections by the agent that worked and `## Response` sections by whoever
reviews. The status is the handshake: `planned` invites, `in-progress`
claims, `review` is a report waiting, `blocked` is a reason waiting,
`done` closes.

Three roles. The person owns what is wanted and the final word. The
delegating agent, usually the session that holds the conversation,
turns wants into briefs, answers plans, reviews and closes. The helper
does a feature's work and reports. A helper is told it is one in its
harness note, and by whom it was started.

A report has four parts: what changed; what was verified and how; what
is left open; what was noticed and left alone. The last part is the
helper's licence to say what it saw outside its scope. Without it, the
first debrief found four such things unsaid, one a defect in the work
just shipped.

## Briefs

A brief names the outcome and what the reader of the result should be
able to conclude, the files and the existing pattern, what not to touch,
the gate, and roughly what the round is worth, so a helper past it stops
and reports rather than grinds. It gives the shape of the result, a
field's type or a table's columns, not the route through the code: a
route sets a helper to doing the sentences it was given and nothing
between them. A `## Response` is a brief and is written to the same
rule; the two costliest rounds on record were Responses that named a
route.

A fact the helper needed and did not have is fixed in the repository's
docs, not repeated in the next brief.

## Running a helper

An agent with a session token starts a helper in its project with
`am new`, sends work with `am turn --quiet`, reads the report and the
commit range, and forgets it with `am delete` once the work is gated.

1. **Orient.** The first turn asks for a reading of `CLAUDE.md`, the
   design doc and `features/`, answered with what was understood and
   what would be questioned. Orientation amortises over conventions;
   a feature in a new part of the code still gets its own reading pass.
2. **Plan, verification first.** Per feature, before any edit: what
   will be hard to verify and how, then how, which files, which
   pattern, and what in the spec to push back on. The delegating agent
   answers every point and says go. On record, plan turns changed the
   design outright once and the implementation in most other rounds,
   at a small fraction of the round's cost.
3. **Three scopes, named apart, every time.** Act within the feature.
   Look anywhere: the repository, its siblings, the daemon's logs. Say
   anything noticed. A helper told only the first collapses the other
   two into it.
4. **Batch.** Several features in one context so orientation pays for
   itself; one commit per feature; one gate. Two per batch is what is
   on record; more is untested.
5. **One writer per repository, per turn.** The delegating agent edits
   a repository the helper writes in only between the helper's turns,
   and says what changed in the next brief. A helper that must touch a
   sibling repository says so in its report, and the delegating agent
   tells that repository's writer before its next turn. Both cases
   happened on the first day and were caught by re-reading, not by
   the rule.
6. **Look at UI work, with both pairs of eyes.** A green suite asserts
   text, not geometry. The brief names the state to screenshot and
   what to measure; the helper does it; the delegating agent does it
   again before the gate. On record, a helper's own screenshot missed
   what the delegating agent's measurement found.

## The gate

Done means the tests and lint pass, the docs that describe the
behaviour are updated, and the work is committed. A feature worked
alone gates itself: full suite, lint, commit, push, deploy. A batch
gates once: cheap checks and a commit per feature, then the full suite
and lint by whoever closes it, who fixes the fallout, pushes and
deploys. Reports say which. Checks are chained so a failure stops the
commit; two commits shipped red on the first day for want of that. A
check that reads git state can pass before the commit and fail after.

## Closing the loop

The delegating agent reviews the commit range and the report, runs the
gate, and records the outcome on the run: accepted, or sent back with a
cause. Four causes: the model did it wrong; the brief was wrong or thin;
a fact the repository's docs should have carried was missing; the
process around the run failed, the delegating agent's own steps
included. The reviewer is usually the briefer and the incentive runs
toward charging the model, so the note says why the cause was chosen.
Two misattributions to the model are on record from the first day, one
of them in the models file.

## Debrief

After a batch, before the helper is forgotten, one more turn: what
worked; what in the briefs was unclear, over-specified or missing; what
it needed and did not have; what it would change here; what it decided
not to say. Read the raw answer beside the summary written of it; the
summary is where the gradient reappears.

## The record

The learnings log takes observations with evidence, at the moment of
noticing, through `am learn`. Rules do not go in it. A curation reads
it and changes this document, and is itself an entry.

The run log records a feature's round from `in-progress` to its end:
agent, model, effort, duration, commit range, spend, transcript, review.
Know what it does not hold. Orientation, plan and debrief turns fall
outside the window, so the method's own cost is not in it. The end
commit is taken when the status changes, which in the normal order of
a report precedes the commit by seconds. The dollar figure on a turn
end in a transcript is the session's running total; a turn's cost is
the difference between two of them.

The models file is a conclusion drawn from the record by hand, by kind
of work, each line carrying the number of runs it rests on and the
effort used. As of today no run has used a non-default effort.

## When not to delegate

Work whose specification is the conversation that produced it, and
anything decided by taste: a screen's layout and wording, the shape of
an interaction, the phrasing of a note. That stays in the session that
holds the conversation, on a frontier model. Delegation pays when the
work can be written down as a feature file; writing it is also the test.
```
